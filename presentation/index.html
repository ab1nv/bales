Bales

A dispatcher for mixed LLM traffic.

Bales sits between users and model servers. It notices when two requests share a prompt, decides whether one should wait for the other, and chooses the GPU that can finish first.

share the reading price the cache hit separate chat and batch
engine-agnostic · OpenAI-compatible · Go 1.27
01 · The problem

The same prompt, read again and again

Before a model can answer, it has to read the whole prompt. That reading step is slow, and it is the same work every time the same document appears.

When many users send one long document at once, a gateway can record a cache entry as soon as it sends the first request. Later requests then believe the document is already in memory and follow the same path. The GPU reads it again, and again, while the users wait.

What goes wrong

  • Copies arrive before the first reading finishes.
  • The router sends followers to the same busy GPU.
  • The reading work is repeated, but no answer comes faster.

Why it matters

  • First answers get slower during bursts.
  • GPU time is spent on duplicate work.
  • The bill rises without a better result.

02 · The aim

    
Three decisions before a request is sent

    
Bales is a dispatcher. It does not run the model. It makes the scheduling decisions that the model server cannot see.

    

      
01
Can we share the reading?
If another request is already reading the same prompt, wait only when the saved work is worth the wait. Otherwise send the request to another GPU.

      
02
Which GPU finishes first?
Compare queue length, cached text, and the cost of reading the missing part. Keep the answer in milliseconds.

      
03
Who goes first?
Give chat a short deadline and batch work a long one. Cap the waiting room so the wait stays finite.

    

    

    
How: build the gateway, test it against mock servers, and use a trace-driven simulator before spending GPU time.

05 · How it works

    
One request, six stops

    

    

      
Standard servers
The GPU side is an OpenAI-compatible server. No custom engine is required for the gateway.

      
No model state
The gateway stores scheduling state only. A restart does not lose weights or KV blocks.

      
Measured, then corrected
Every prediction is recorded and compared with the engine's cached-token report.

    

  






  

    
06 · Reading cost

    
Reading a prompt has a price

    

      

        
A cache hit removes the reading work for the shared part. The saved time is the price of that reading, and it grows faster than the prefix because attention also grows.

        

        

        

          
warm request178 ms

          
cold request439 ms

          
saved261 ms

          
attention share41%

        

        
The simple form: reading cost = attention over shared text + attention over new text + fixed work. A token is a small piece of text, roughly a word piece. The full model is fitted per deployment.

      

      

        
same request, with and without the shared prefix

        

        
The gold delay is the budget available for waiting. Bales holds a follower only when the saved block is larger than the wait.

08 · Who goes first

    
Two lanes, one waiting room

    

      

        
Chat needs a short deadline. Batch work can wait, but it must not wait forever. Bales gives each request a fixed deadline and serves the earliest one first.

        

        

        

        
cap the waiting room + order by deadline = a finite wait

        
With a 5 s batch deadline, earliest-deadline-first behaves almost like strict priority. Shortening the batch deadline creates a real tradeoff between chat latency and batch progress.

09 · Pick a GPU

    
Pick the GPU that finishes first

    
Reading time, queue time, and interference are added in milliseconds. The smallest number wins. KV capacity and a latency guard can remove a candidate.

    

      
      
    

    

    
ECT chooses GPU 2: a small queue beats a larger cache on GPU 0.

  






  

    
10 · Keep or spread

    
Affinity has a cost

    

      

        
Sending a prefix group to one GPU keeps the cache hot. It can also overload that GPU. The gate chooses spread, pin, or replicate from the work the cache saves.

        

        

        
REPLICATE2 replicas, recoverable 1566 ms/s

        
Single-pin affinity was two to three times worse than round robin on hot traces. The gate prescribes replicate for those groups.

      

      

        
load on four GPUs

        

        
The compact pattern is the load. The gate decides whether to concentrate it or spread it.

What we need to reach the target

Measure duplicate prefill, fit the cost model on an idle replica, run the burst on real hardware.
unlocks H1, H4

Add continuous decode batching and compare against two real replicas. The gate is 10 percent MAPE.
unlocks large-R claims

      
3Tuned baselines
Give llm-d, Dynamo, DualMap, Preble, and CacheRoute the same tuning budget as Bales.
unlocks fair comparison

      
4Gated affinity and nested prefixes
Wire the gate into a routing policy and extend coalescing to shared prefixes with different suffixes.
unlocks C1, C4

Add a threat model for timing leaks and a precise cache mode from engine events.
unlocks deployment
