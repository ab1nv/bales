Part I. The project in plain terms

1. What Bales is

Bales is a gateway that sits in front of a group of LLM inference servers. Clients send it OpenAI-style chat requests. Bales decides which server should handle each request, whether the request should wait for another request that is already computing the same prompt, and when a batch job should be allowed to run relative to an interactive chat.

The project exists because three problems appear when several LLM requests share a cluster. First, the same long prompt often arrives more than once at nearly the same time. The servers can reuse the computed prefix through a KV cache, but only after the first copy has been processed. Requests that arrive during that window may be sent to the same server and made to wait, or sent to different servers and made to compute the same prefix again. Second, not all cache hits are worth the same. A hit on a short system prompt saves little. A hit on an 8,000-token document saves a lot of attention work. A router needs a calibrated price for the hit rather than a fixed bonus. Third, interactive chat and batch jobs need different latency treatment. A single first-come queue lets long batch work block short chat requests. A hard priority rule protects chat but can starve batch work forever.

2. The problem in one picture

client A ─┐
client B ─┼── same 2k-token prompt ──▶ router
client C ─┘                              │
                                         ├── sends all three to GPU 0
                                         │   because the cache entry
                                         │   was recorded at dispatch
                                         ▼
                                   GPU 0: prefill 2k tokens
                                          prefill 2k tokens again
                                          prefill 2k tokens again

The router is not lying on purpose. It recorded the cache entry when it sent the first request, which is what production routers do to let the next request find the same replica. The engine has not finished the prefill yet, so the entry is a belief; the engine has not confirmed it yet. Bales makes that distinction explicit and adds one missing decision: should the follower wait for the leader, or move to another GPU?

3. What the prototype does

  • Hashes the prompt into tenant-salted blocks. The final hash identifies the full chain and becomes the coalescing key.
  • Admits the request under a cap on queued estimated work, then assigns a static virtual deadline. Streams get a short base deadline; batch jobs get a long one.
  • Coalesces same-prompt requests. A follower waits only when the saved prefill is larger than the wait. The wait is capped by the request slack and by a deployment maximum. Otherwise the follower spills to another replica.
  • Prices the prefill with a fitted cost model and routes by earliest completion time, with KV and inter-token-latency guards.
  • Audits its own cache belief against the number of cached tokens reported by the engine, and records every request in a CSV ledger.

5. What the prototype does not prove

There are no GPU measurements yet. The cost coefficients are plausible defaults, not T4 measurements. The simulator is useful for relative comparisons but it overstates queueing because it does not batch decode across requests. The llm-d, Dynamo, CacheRoute and Preble baselines are simplified and untuned, so the prototype cannot claim a win over those systems. The coalescer matches exact prompt chains, not nested prefix groups with different suffixes. The affinity gate is implemented as a decision function and tested, but a gated routing policy is not yet wired into the simulator.

Two planned claims did not survive. The quadratic cost term did not improve routing on its own in the tested regime; the queue and the cache-hit value did the work. EDF did not dominate strict priority when the class deadlines were far apart. Both results are useful: they tell the next phase where to spend effort.

6. Why the project is interesting

The prototype takes a problem that production systems currently solve in three different places, inside the engine, inside the router, and inside the application, and moves one decision to a shared gateway. If the gateway can coalesce in-flight prompts without depending on the engine, the same mechanism works across vLLM, SGLang, and any OpenAI-compatible server. The real-hardware test is the next step.

Part II. Technical background

7. Prefill, decode, TTFT and ITL

An LLM request has two phases. Prefill processes the whole prompt and builds the KV cache. It is compute-bound and its cost grows with prompt length; attention cost grows with the product of new tokens and cached context. Decode generates one token per step and is memory-bandwidth-bound. The first output token cannot appear until prefill finishes, so prefill sits directly on TTFT, the time to first token. ITL is the gap between output tokens. A large prefill can inflate the ITL of other requests that share the GPU, which is why the router has an ITL guard.

8. Prefix caching and the belief problem

A prefix cache stores the KV state of earlier tokens. If a later request starts with the same tokens, the engine can skip that part of prefill. Routers keep a directory of which prefixes live on which replica. The directory is only a belief. When a request is dispatched, the engine has not finished the prefill, but the router often records the entry immediately so that the next request follows the same path. This is speculative indexing. It is useful when the next request arrives after the prefill finishes. It is harmful when followers arrive during the prefill, because they are sent to the same replica and duplicate the work.

Bales keeps two things apart: the speculative belief used for routing and the actual cache used for prefill cost. The simulator does the same. That gap is the mechanism behind the burst result.

9. The cost model

cost(q, c) = a·q·c + b·q(q+1)/2 + f·q + g

q is the number of new query tokens, c is the cached context those tokens attend to, and g is fixed overhead. The first term is attention to the cached context. The second is causal attention inside the new chunk. The third is the linear feed-forward and projection work. The coefficients are fitted per model, engine, and GPU with non-negative least squares on idle-replica measurements.

For a cached prefix of length L, the work avoided is:

saving = cost(q + L, 0) - cost(q, L)

When the two attention coefficients are equal, this simplifies to the prefill cost of L, which is the clean statement of the cache-hit value. The prototype uses the exact difference so the rule remains correct after calibration.

10. Hold or spill

hold iff  saving(L) - τ - (wait_leader - wait_best) > ε
deadline = min(1.5·τ, slack, delta_max)

τ is the leader's remaining prefill. The follower waits only when the saved work is larger than the wait it adds. The hold deadline bounds the regret: a held follower can be delayed by at most the deadline relative to spilling immediately. If an idle replica is available and the leader has just started, spilling is often the better choice for that request's latency; holding is better when replicas are contended or the leader is nearly done. The rule chooses per request instead of applying one policy to the whole burst.

11. Virtual deadlines and the wait bound

d_i = arrival_i + D_class + eta · estimated_cost_i

Deadlines are static. The queue orders by a fixed key, so insertion is O(log n) and the heap never needs to be rebuilt as time passes. Streams use a short base deadline, batch jobs a long one. Under admission control the wait of a request is bounded by:

W_i ≤ (Q_max + A(delta_i)) / C + s_max

Q_max caps queued work, A is the arrival curve of requests that can outrank the tagged request inside its overtaking window, C is pool capacity, and s_max is the largest non-preemptive job. The prototype fuzzes this bound over 200 randomized traces.

One result is worth remembering: when the batch deadline is much larger than the stream deadline, EDF behaves almost like strict priority. It only differs for requests that arrive after the batch deadline has passed. The queue experiment shows this. Shortening the batch deadline creates a real tradeoff between batch wait and stream latency.

12. ECT and the affinity gate

ECT = queue_wait + cost(uncached, cached) / speed + interference

Every term is in milliseconds, so there are no unitless weights in the main score. The router rejects placements that would exceed KV capacity or inflate ITL beyond a budget. If every replica is rejected, it falls back to the least loaded healthy replica.

The affinity gate compares recoverable work, rate × saving(prefix), with a fraction of cluster capacity. It spreads when the recoverable work is small, pins when one replica can carry the group, and replicates when the group needs more than one. The simulation showed why this matters: a single-pin policy was two to three times worse than round robin on hot traces.

Part IV. Demo, questions, and cheat sheet

14. Running the demo

make build
make demo

The demo starts two mock workers and the gateway, sends four staggered copies of one prompt, and prints the counters and a few telemetry rows. Point out three things: the leader, the released followers, and the spill. Then show the audit precision and recall of 1.0 on that run. The full CSV is at evidence/runs/demo.csv.

If someone asks to see the tests, run make ci or go test ./.... The race suite is go test -race ./.... The simulator is ./bin/bales-simulate -exp all -out evidence/runs -seeds 3.

15. Likely questions

Is this novel? The ingredients are not. Quadratic cost models, prefix routing, leader/follower waits, and deadline queues all exist. The prototype combines them at the gateway and makes the hold decision explicit and bounded. The evidence is a prototype result.

Why no GPU results? Scope. The first phase was designed to be falsifiable on a CPU and in simulation. The next gate is a T4 and vLLM run. The report labels every cluster number as simulated.

Why is the quadratic term not helping? At 2k tokens, the attention term is second-order against the linear term. The long-context gap in the simulation comes mainly from queue-aware ECT, not from the quadratic shape. The model still matters for valuing long cached prefixes, which is why it stays in the hold rule.

Why did EDF lose? With a 5-second batch deadline and a 300-millisecond stream deadline, EDF behaves like strict priority. The interesting regime is a shorter batch deadline, where batch wait falls and stream latency rises. That is a policy choice; the bound still holds.

Is coalescing safe across tenants? The prototype salts hashes per tenant and coalesces only within a salt. The timing side channel is real: a cross-tenant hold could reveal that another tenant sent a prefix. The tenant salt is the default mitigation; a production deployment needs a threat model and a separate security review.

What happens if the leader dies? The group is closed as failed and waiting followers spill on their deadline. The registry completion is idempotent, and the gateway has race tests for the registry and integration tests for the follower path.

What about PEEK? PEEK is the closest engine-side cousin. It solves pending-queue duplication inside one engine. Bales moves the decision above the engine so it can span replicas and engine types. A production system could use both.

What is the business case? Less duplicate prefill means more useful GPU seconds and lower follower TTFT during bursts. The Cloudflare postmortem shows an application-layer version saving money. The prototype has not priced a deployment; that is future work.

What would break at scale? Directory divergence, KV pressure, trace fidelity, and baseline tuning. The auditor and the simulator fidelity gate are the first defenses. The current simulator has not been validated against a GPU.

17. Two-minute version

If you have two minutes, say this. Bales is a gateway for mixed LLM traffic. When several requests share a prompt, a router can record a speculative cache entry and send every follower to the same replica, where the engine duplicates the prefill. Bales adds a hold-or-spill decision at the gateway: wait for the leader only when the saved prefill beats the wait, otherwise use a spare GPU. It prices the hit with a calibrated cost model and gives stream and batch traffic separate virtual deadlines. In a simulated cold burst of 32 requests, coalescing cut P50 TTFT from 505 to 143 milliseconds and prefill work by 87 percent. The prototype is tested and reproducible, but the cluster results are simulated; the next step is a T4 and vLLM run.
